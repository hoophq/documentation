---
title: "Identity & Credentials"
description: "Every field of identity, credentials, select, context, passthrough_users, propagate and credential_set."
---

A listener that terminates the client's login carries up to five blocks. `identity` names how the client proves who it is. `credentials` names the pool the Sidecar logs in upstream with and how a verified identity picks one entry. `context` is what the rules and the audit trail know about the lane. `passthrough_users` is the exception list. `propagate` carries the person to the upstream beside the swapped credential. The sources a pool draws from are declared once, at the top level, under `credentials`.

The concept, with a worked example per protocol, is in [Credential Swap](/features/credential-swap). This page is the field list.

Every key here is served by the Control Plane only to a Sidecar whose build declares it, and a build that lacks a key refuses the whole document rather than running half of it. A listener carrying none of these blocks behaves as it did before they existed.

---

## Top level: `credentials`

Which sources this process has. A pool entry names one by its key here.

```yaml
credentials:
  secret_files: {dir: /run/hoop-creds}
  gcp_impersonation: {}
  x509: {}
  spiffe: {socket: unix:///run/spire/sockets/agent.sock}
  kerberos: {cache: /run/krb5/ccache, config: /etc/krb5.conf}
```

| Source | Fields | Notes |
|---|---|---|
| `secret_files` | `dir` | Every `user_file` and `password_file` of a pool entry is relative to it. Files are re-read on every login. A password file readable by group or other is refused at startup. |
| `gcp_impersonation` | `metadata_host` | Empty is `metadata.google.internal`. The process's own identity from the metadata server mints the access token through `iamcredentials.googleapis.com`. |
| `x509` | none | Its presence configures the source; the files are per pool entry. |
| `spiffe` | `socket` | Workload API address. Empty is `unix:///run/spire/sockets/agent.sock`. Linked into `hoop-inspect` only; a build without it refuses the key. |
| `kerberos` | `cache`, `keytab`, `config` | Exactly one of `cache` or `keytab`. `config` is the krb5.conf path, default `/etc/krb5.conf`. The cache is re-read on every login, so the platform can rotate it. Linked into `hoop-inspect` only. |
| `vault` | `addr`, `auth`, `ca_file`, `namespace` | HashiCorp Vault over https. `auth.type` is `kubernetes` (the pod's service account token, `auth.role`, optional `auth.mount` and `auth.token_file`) or `token_file` (`auth.token_file`). A Vault token written in the configuration is refused. |
| `gcp_secret_manager` | `metadata_host` | Secret Manager, with the pod's Workload Identity as the caller. |

A pool entry whose `source` names a block that is absent here fails startup, naming the lane and the entry.

## Listener: `identity`

| Field | Types | Meaning |
|---|---|---|
| `type` | | `none`, `kubernetes`, `hoop_credential`, `jwt` or `spiffe` |
| `audience` | `kubernetes`, `jwt`, `spiffe` | The audience the token must carry. Empty is `hoop-sidecar`. |
| `issuer` | `kubernetes`, `jwt` | The token's `iss`. For `kubernetes`, the API server URL; empty is the in-cluster `https://kubernetes.default.svc`, reached with the mounted CA and service account token. For `jwt`, required, an `https` URL. |
| `jwks_url` | `jwt` | Where the issuer's keys are read. Empty runs OIDC discovery at `<issuer>/.well-known/openid-configuration`. |
| `claims` | `jwt` | Which claims become the identity: `subject` (default `sub`), `email` (default `email`), `groups` (default `groups`; a string or a list). The subject claim must be present. |
| `trust_domain` | `spiffe` | Refuses a SPIFFE ID outside it. |
| `prefix` | `spiffe` | Refuses a SPIFFE ID whose path is not under it. Path-segment aware: `/ns/payments` does not admit `/ns/payments-sandbox`. |

What each type verifies, and what the identity it produces carries:

| Type | Verifies | Identity |
|---|---|---|
| `none` | nothing; the unix socket is the boundary | subject from `context.owner` when set; the lane's context as attributes |
| `kubernetes` | the signature against the issuer's JWKS (OIDC discovery), `aud`, `exp`, `nbf`, `iss`; when `POD_UID` is set in the environment, the token's `kubernetes.io.pod.uid` must equal it | `subject` = the token's `sub`; attributes `namespace`, `pod`, `service_account` |
| `hoop_credential` | `sha256(key)` against the lane's entries of `credential_set`, in constant time; expiry; the login user must be the entry's subject or email | subject, email and groups of the entry |
| `spiffe` | the JWT-SVID through the Workload API, then `trust_domain` and `prefix` | `subject` = the SPIFFE ID; attributes `trust_domain`, `path` |
| `jwt` | the signature against the issuer's JWKS, `iss`, `aud`, `exp`, `nbf`; on a protocol with a login user, the user must be the token's subject or email | subject, email and groups from the mapped claims; attribute `issuer` |

Rules the validator enforces:

- `identity` is exclusive with `identity_header`, `google_identity` and `caller_token` on one listener.
- `identity` needs a `credentials` pool: a verified login with nothing to present upstream does nothing.
- `type: none` needs `network: unix`.
- `type: hoop_credential` or `type: jwt` on a TCP `postgres`, `mysql` or `clickhouse` listener needs `downstream_tls`.
- `type: jwt` needs `issuer`; `jwks_url` and `claims` are refused on any other type.
- A listener with a pool and no `identity` is accepted on a unix socket alone, where it means `none`.
- A type the build does not link (`spiffe` outside `hoop-inspect`) is refused with the reason.
- On an `oracle` listener only `type: none` is accepted, and no pool.

## Listener: `credentials`

```yaml
credentials:
  pool:
    - {name: rw, source: secret_files, user_file: appdb-rw/user, password_file: appdb-rw/password}
    - {name: ro, source: secret_files, user: app_ro, password_file: appdb-ro/password}
    - {name: svc, source: gcp_impersonation, service_account: svc@proj.iam.gserviceaccount.com, scopes: [https://www.googleapis.com/auth/cloud-platform]}
    - {name: cert, source: x509, cert_file: /etc/hoop/appdb/client.crt, key_file: /etc/hoop/appdb/client.key}
    - {name: svid, source: spiffe, spiffe_id: spiffe://corp/db/appdb-ro}
    - {name: krb, source: kerberos, principal: svc-hoop@CORP.EXAMPLE}
  select:
    rules:
      - {when: {identity.groups: dba, context.env: prod}, credential: rw}
      - {credential: ro}
```

### `pool`

One entry per credential the listener may present. `name` is what `select` picks and what the audit trail records as `credential`. `source` names a top-level block. The other fields depend on the source:

| Source | Entry fields | Presents upstream |
|---|---|---|
| `secret_files` | `user` or `user_file`; `password_file` | user and password |
| `gcp_impersonation` | `service_account`, `scopes` | the account as user, the access token as password; a bearer on `http`, `grpc`, `spanner` |
| `x509` | `cert_file`, `key_file`; `user` defaults to the certificate's common name | a client certificate |
| `spiffe` | `spiffe_id`; `user` optional | a client certificate (the X509-SVID with that ID) |
| `kerberos` | `principal` (required with a keytab; must match the cache's principal when set with a cache) | a GSSAPI initiator; `user` is the principal |
| `vault` | `path`; for a KV path `user_key`/`password_key` (default `user`/`password`) or a literal `user` | user and password, read at every login. A database engine path (`database/creds/<role>`) yields a user Vault creates for the session; the sidecar revokes its lease when the session ends. Not valid on `http`, `grpc` or `spanner`, which swap per request |
| `gcp_secret_manager` | `secret` as `projects/<p>/secrets/<s>/versions/<v>`; `user` optional | the payload as the password when `user` is set, else a JSON document holding `user` and `password` |

An access token from `gcp_impersonation` is cached per entry until five minutes before it expires. Everything else is read at login.

### `select`

Exactly one of `rules` or `opa: true`.

`rules` is an ordered list; the first whose `when` matches picks the credential; no match refuses the login. `when` is a conjunction over:

| Key | Matches when |
|---|---|
| `identity.subject` | the subject equals the value |
| `identity.email` | the email equals the value |
| `identity.groups` | the groups contain the value |
| `identity.attributes.<k>` | attribute `k` equals the value (`namespace`, `pod`, `service_account` from a Kubernetes token; `trust_domain`, `path` from a SPIFFE ID) |
| `context.<k>` | the lane's `context` key `k` equals the value |

An empty `when` matches everyone, which is how the last rule becomes the default.

`opa: true` asks the listener's OPA endpoint with a `login` statement whose `input.context` carries the identity and the lane context, and reads `credential` beside `allow` in the answer. The listener needs an `opa` block.

## Listener: `context`

A map of strings the lane knows about itself. Every key is available to `select` as `context.<k>`, to `propagate.application_name` as `.Context.<k>`, and to OPA under `input.context`. On a `type: none` listener, `context.owner` becomes the subject of every session.

```yaml
context: {owner: jane@acme.com, env: prod, project: billing}
```

---

## Listener: `passthrough_users`

Upstream user names the Sidecar relays unchanged, with the password the client holds. The login is recorded with `verified: false`. A startup user not on the list is refused at the door, whatever password it carries. On `mssql`, the entry `integrated` relays Windows (SSPI) logins, whose user name the Sidecar cannot read.

```yaml
passthrough_users: [legacy_etl, integrated]
```

Needs `identity`; alone on a listener it is refused.

## Listener: `propagate`

| Field | Protocols | Meaning |
|---|---|---|
| `application_name` | `postgres` | A template for the startup parameter, over `.Principal`, `.Email`, `.Subject` and `.Context.<k>`. Example: `"{{.Principal}} via {{.Context.env}}"`. |
| `impersonate_user` | `http` | Adds `Impersonate-User` (the email, else the subject) and one `Impersonate-Group` per group toward a Kubernetes API server, so its audit log and RBAC see the person. The service account the pool presents needs the `impersonate` verb. |

A listener with a pool always drops client-sent `Impersonate-*` headers on `http`, whether or not `impersonate_user` is on.

## Top level: `credential_set`

What `hoop_credential` verifies against. The Control Plane composes it into the served document from the keys users minted for this Sidecar; it is never authored by hand except for a standalone demo. The heartbeat swaps it in place, so a mint or a revocation is in force at the next login without a restart, and the set never takes part in the restart comparison.

```yaml
credential_set:
  - hash: 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
    subject: jane@acme.com
    email: jane@acme.com
    groups: [dba]
    lane: appdb
    expires_at: 2026-11-01T00:00:00Z
    scram: {salt: ..., iterations: 4096, stored_key: ..., server_key: ...}
```

| Field | Meaning |
|---|---|
| `hash` | hex SHA-256 of the raw key; the key itself never travels |
| `subject`, `email`, `groups` | the identity the login produces |
| `lane` | the listener name the key is valid for |
| `expires_at` | refused after this instant, by the Sidecar's clock |
| `scram` | the SCRAM-SHA-256 server verifier (base64 salt and keys, iteration count) the `postgres` and `mongodb` drivers use when the client leg cannot carry the key in clear |

---

## What the audit trail carries

Every `session_start` on a listener with `identity` adds four metadata keys: `identity_type`, `credential` (the pool entry name), `upstream_user`, and `verified` (`true`, or `false` on a pass-through). A refused login is a one-event session under the claimed user with a `violation` whose rule is `identity`. The Sidecar's `/stats` and the Control Plane's Sidecar page show which `identity:<type>` and `credentials.<source>` entries the build declares.
