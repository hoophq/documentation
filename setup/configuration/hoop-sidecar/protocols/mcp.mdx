---
title: "MCP"
description: "A protocol: mcp lane in front of one remote MCP server: tool policy, SQL tools, guardrails, OPA, metrics and one audited session per MCP session"
---

A `protocol: mcp` lane terminates MCP streamable HTTP on `/mcp` and forwards to one remote MCP server over `streamable-http` or `sse`. It hides the tools a rule denies, judges each `tools/call` with the lane's guardrails and OPA, and records one Sidecar session per MCP session.

The lane embeds [mcpproxy](https://github.com/hoophq/mcpproxy) and ships in Sidecar 1.289.0 and later. A Sidecar build without the MCP engine refuses the lane at `-validate`.

---

## Configure a lane

```yaml config.yaml
listeners:
  - name: github-mcp
    protocol: mcp
    listen: 127.0.0.1:18901      # loopback; another address needs caller_token
    upstream: https://mcp.example.com/mcp   # a server that needs no credential; see Auth
    idle_timeout_sec: 1800       # an idle MCP session ends after this; default 30 minutes
    guardrails:                  # which tools the lane offers; see Tool allow and deny
      rules:
        - {name: no-delete-tools, type: mcp_tool, tools: ["*delete*"], message: deleting through MCP is not allowed}
        - {name: read-only-tools, type: mcp_tool, allow: ["get_*", "list_*", "search_*"]}
    mcp_gateway:
      transport: streamable-http # or sse
      block_sampling: true
      block_elicitation: true
      on_rug_pull: kill
      max_calls_per_session: 200
      max_result_kb: 256
      tool_rate_limits: {"search_*": 30}
      overrides:
        get_file_contents: {description: Read one file from a repository.}
```

The MCP client points at `http://127.0.0.1:18901/mcp`.

## Listener keys

| Key | Default | Effect |
|---|---|---|
| `listen` | required | `host:port` on loopback: `127.0.0.1`, `::1` or `localhost`. Any other address needs `caller_token`. MCP clients connect to `http://<listen>/mcp`, or `https://` with `downstream_tls`. |
| `upstream` | required | The MCP endpoint, with its path. `https`, or `http` on loopback. No user, password, query or fragment. A redirect is followed only within its origin. |
| `upstream_tls` | the host trust store | The CA, the client certificate and the server name for the hop to the upstream. |
| `idle_timeout_sec` | `1800` | An MCP session with no message for this long ends, with its Sidecar session. |
| `identity_header` | none | The header whose value names the caller. See [Auth](#auth). |
| `caller_token` | none | Admits only a caller that sends a listed token. See [Caller token](#caller-token). |
| `downstream_tls` | none | Terminates the client's TLS at the lane: `cert_file` and `key_file`. HTTP/1.1 over TLS 1.2 or later. |
| `guardrails`, `opa` | the top-level blocks | The rules and OPA for this lane. `mcp_tool` rules decide which tools it offers. |
| `mask` | the top-level block | The mask rules for tool and resource results. See [Masking](#masking). |
| `analyzer` | none | A model rates each tool call. The provider and model come from the top-level `analyzer` section. See [AI analyzer](#ai-analyzer). |
| `mcp_gateway` | none | The upstream transport and the session policy. See below. |

## Tool allow and deny

A guardrail rule of type `mcp_tool` decides which tools a lane offers. `tools` lists the tools it denies; `allow` lists the only tools it lets through. A rule sets one of the two.

```yaml config.yaml
guardrails:
  rules:
    - {name: no-delete-tools, type: mcp_tool, tools: ["*delete*"]}
    - {name: read-only-tools, type: mcp_tool, allow: ["get_*", "list_*"]}
```

The lane leaves out of `tools/list` every tool an `mcp_tool` rule denies, so the model never sees it. The catalog statement names the hidden tools in `mcp.tools_hidden`.

A call to a hidden tool is denied like any rule denial: a tool result with `isError: true` and the text `denied by the hoop sidecar (rule <name>): <message>`. MCP reports a failed tool call this way, as a result rather than a JSON-RPC error, so the model sees the denial and its message.

A `tools/list` result the lane cannot read ends the session and records `mcp_catalog_unreadable`: the lane could neither hide tools from it nor judge it.

With `action: defer`, an `mcp_tool` rule hides nothing, and OPA decides each call: without OPA, a deferring rule denies the call.

Two `allow` rules let through only the tools both list.

A `tools/call` is judged by its exact `name` key. Params that name no tool, or carry keys that differ only in case, are refused as invalid params (`-32602`) and recorded as `mcp_invalid_params`.

Other rule types and OPA judge calls too, and hide nothing.

A glob has one metacharacter: `*` matches any run of characters, including none. Every other character matches literally, and case counts: `*delete*` matches `bulk_delete_rows`, and `get_*` does not match `Get_file`.

The rule reads the real tool name, not the name `overrides` gives it.

An `mcp_tool` rule in the top-level `guardrails` reaches every mcp lane, and other lanes ignore it. A lane's own rules run first and the top-level ones after them; `rules: []` on the lane drops the top-level ones.

A rule edit applies without a restart and ends the open MCP sessions; the next session gets the new catalog. On a managed sidecar, the Guardrails page of the control plane offers it as the rule type **MCP tool** on an MCP listener, from version 1.300.0.

## `mcp_gateway` keys

| Key | Default | Effect | The client gets |
|---|---|---|---|
| `transport` | `streamable-http` | How the lane reaches the upstream: `streamable-http` or `sse`. | |
| `overrides` | none | Per tool: `name` renames it and `description` replaces its description in `tools/list`. A call to the new name reaches the real tool. | |
| `block_sampling` | `true` | Refuses the server's `sampling/createMessage` requests, which ask the client's model to generate text. | Nothing: the client never sees the request, and the server gets `-32010`. |
| `block_elicitation` | `true` | Refuses the server's `elicitation/create` requests, which ask the user for input. | As for `block_sampling`. |
| `on_rug_pull` | `kill` | A rug pull is a later `tools/list` that changes the description or input schema of a tool this session already listed. `kill` ends the session; `alert` records it and goes on. A tool an `mcp_tool` rule hides never counts. | `kill`: `-32010` with the reason, then 404 on the session |
| `max_calls_per_session` | `0`: no limit | The tool calls one MCP session may attempt. A refused call counts too. | Past the limit: `-32012`, `session tool-call budget exhausted (N calls)` |
| `tool_rate_limits` | none | Tool glob to calls per minute, per session. When several globs match a tool, the lowest limit applies. | Over the limit: `-32012`, `tool "x" rate limit exceeded (N calls/min)` |
| `max_result_kb` | `0`: no limit | The text of a tool result is cut to this size and ends with `[truncated by gateway]`. | The cut result |
| `sql` | none | The tools whose calls carry SQL. See [SQL tools](#sql-tools). | |

`tool_rate_limits` globs work as in `mcp_tool`.

Once the session has listed tools, a call to a tool the server did not list is refused too: `-32010`, `tool "x" was not advertised by the server`.

A call these keys refuse, a truncated result and a rug pull reach the Sidecar session as activities: `mcp.tool_denied`, `mcp.budget_exceeded`, `mcp.tools_changed`.

A key the block does not map, such as `allowed_tools` (an `mcp_tool` rule instead), `approval_tools`, `command` or `headers`, fails as `unknown field`.

## What the rules read

Each `tools/call` is one statement: `operation: call`, `tables: [<tool>]` in lower case, the text `<tool>` with its arguments JSON on the next line, and the metadata `mcp.method`, `mcp.tool` and `mcp.session`.

A call to a [SQL tool](#sql-tools) adds one statement per SQL statement in its argument.

```yaml config.yaml
guardrails:
  rules:
    - {name: no-delete, type: mcp_tool, tools: ["*delete*"]}                    # the tool name; hides it too
    - {name: no-prod, type: deny_words_list, words: [prod-db]}                # tool name and arguments
    - {name: no-prod-db, type: pattern_match, pattern_regex: '"db":\s*"prod-'}  # tool name and arguments
    - {name: no-calls, type: operation, operations: [call]}                   # every tools/call
```

The metadata names the tool in the audit trail and in OPA's input.

Each `tools/list` is one catalog statement: `direction: server`, `operation: show`, no tables, one `<name>: <description>` line per tool.

Rules and OPA judge the catalog too, and a hit ends the session. A `deny_words_list` word in a tool description ends it.

A `table` rule never matches the catalog, `require_table_match` included.

[Policy Rules](/setup/configuration/hoop-sidecar/policy-rules) describes each rule type.

## SQL tools

`mcp_gateway.sql` names the tools whose calls carry SQL. The lane's rules then read that SQL as on a SQL lane. Sidecar 1.302.0 and later; older builds refuse the key at `-validate`.

```yaml config.yaml
listeners:
  - name: bigquery
    protocol: mcp
    listen: 127.0.0.1:18902
    upstream: http://127.0.0.1:18903/mcp   # a loopback proxy that adds the credential; see Lane to upstream
    guardrails:
      rules:
        - name: read-only
          type: operation
          operations: [insert, update, delete, merge, create, alter, drop, truncate, other, unknown]
          message: this lane is read-only
    mcp_gateway:
      sql:
        "execute_sql*": {argument: query, dialect: googlesql}
```

| Key | Effect |
|---|---|
| the key | A tool glob, as in `mcp_tool`. It reads the real tool name. When several globs match a tool, the longest wins. |
| `argument` | The top-level argument that holds the SQL. Required. |
| `dialect` | `postgres`, `mysql`, `mssql`, `clickhouse`, `googlesql`, `oracle` or `spark`. Required. BigQuery is `googlesql`. |

`-validate` refuses an entry without a glob, an argument or a known dialect. The lane never guesses the dialect.

A call to a SQL tool is 1 + N statements, judged in order: the call statement, then one statement per SQL statement in the argument. The first deny stops the call, and the client gets it as for any rule denial.

Each SQL statement carries the SQL as its text, and the operation, effects and tables the lexer reads. [What the audit records](#what-the-audit-records) lists its metadata.

`mcp_tool` rules read only the call statement. A `table` rule reads the tables of the SQL, and `require_table_match` denies a SQL statement that names none. Observe mode records all 1 + N.

To scope a rule to one tool, use OPA or a [`metadata`](/setup/configuration/hoop-sidecar/policy-rules#metadata) rule on `mcp.tool`.

SQL the lexer cannot read is `operation: unknown`, as on a SQL lane: `EXECUTE IMMEDIATE`, a script loop or block, `EXPORT DATA`. A rule must name `unknown` to refuse it.

With `googlesql`, a script part that starts with `LOOP`, `WHILE`, `REPEAT`, `FOR` or a `BEGIN` block, also after a label, is `unknown` with its writes as effects: a rule naming `delete` refuses a `DELETE` in a loop. A bare `BEGIN` and `BEGIN TRANSACTION` are not scripts.

The lane refuses a call before any rule, also in observe mode, when it cannot read the argument:

- `arguments` is absent or not an object.
- The argument, by its exact name, is absent, not a string, blank or holds no statement.
- The argument appears two times, also after JSON unescape or in another case.
- The argument holds invalid UTF-8 or a lone surrogate escape.
- Two globs of the same length match the tool and disagree.

The client gets `denied by the hoop sidecar (rule mcp_gateway.sql): <reason>`, and the session records `mcp_sql_unreadable`.

A Sidecar managed by a Control Plane gets `sql` only when it reports the `mcp_sql` capability.

## OPA

With an `opa` block, the lane consults OPA on every call and on the catalog. The input for a call, beside the `context` every lane sends:

```json
{"protocol": "mcp", "direction": "client", "operation": "call",
 "tables": ["get_file_contents"], "statement": "get_file_contents\n{\"path\":\"README.md\"}",
 "metadata": {"mcp.method": "tools/call", "mcp.tool": "get_file_contents", "mcp.session": "<id>"}}
```

`responses: false` keeps the catalog from OPA:

```yaml config.yaml
    opa:
      url: http://opa:8181/v1/data/hoop/inspect
      responses: false
```

## Masking

The lane masks tool and resource results with its [mask rules](/setup/configuration/hoop-sidecar/config-file#masking). It masks these strings of a `tools/call`, `resources/read` and `tasks/result` result:

- `content[].text`
- `content[].resource.text`, an embedded resource
- `contents[].text`
- every string of `structuredContent`, up to 128 levels deep

Object keys, numbers and other fields are not masked: the client reads them as protocol. Prompts and upstream error messages are not masked.

```yaml config.yaml
    mask:
      rules:
        - {name: emails, entities: [EMAIL_ADDRESS], strategy: redact}
        - {name: cards, entities: [CREDIT_CARD], strategy: partial, keep_last: 4}
```

- Rules find values by entity. The lane gets each string without its key, so a `columns` rule never matches. `-validate` refuses one in the lane's `mask` block. An inherited one does not apply on the lane, and `-validate` says so; inherited entity rules apply.
- Each masked result is one `masked` audit row with the count and the entities, never the values.
- The client gets JSON-RPC error `-32010` instead of the result, and the MCP session stays open, when the masker fails, its audit row cannot be written under `fail_on_audit_error`, a key repeats or differs only in case, `structuredContent` nests deeper than 128 levels, or the result or a field above has an unexpected type (an object where an array belongs). A `null` passes.
- Turning masking on or off needs a restart. A rule change applies without one.
- A Sidecar managed by a Control Plane gets mask rules on an mcp lane only when it reports the `mcp_mask` capability. The Data masking page offers MCP listeners and binds entity rules only.

## AI analyzer

An `analyzer` block, or an `ai_analysis` rule, classifies each `tools/call`. See [Risk Analysis](/setup/configuration/hoop-sidecar/risk-analysis) for the block. The model reads the tool name and the arguments JSON, cut to `max_input_bytes` (default 8 KiB). It never reads `tools/list` or a result.

```yaml config.yaml
    analyzer:
      trigger: {operations: [call]}   # omit it to classify every call
      high: block
      medium: warn
```

- `block` refuses the one call as a tool error. The MCP session stays open.
- A hold refuses the call before any approver, the AI agent included, and files no approval request: the lane cannot hold a call for approval yet. A hold that a person approves still needs a reviewer to start, as on the other lanes: a Control Plane with an approval rule, or a terminal reviewer.
- A provider failure follows `fail_open`, as on the other lanes.
- On a [SQL tool](#sql-tools), the model reads the call and each SQL statement of its argument: one model call for the call and one per statement.
- The statement row carries `risk_level`, `risk_action`, `ai_rule` and `ai_status`.
- A Sidecar managed by a Control Plane gets an analyzer on an mcp lane only when it reports the `mcp_analyzer` capability. The AI Analyzer page offers MCP listeners, with "Hold for approval" disabled.

## Sessions and audit

One Sidecar session per MCP session. It opens on the first message and closes on the client's `DELETE` or the idle timeout.

The session records `initialize` as an activity (client name, version, protocol version), one statement per `tools/call`, allowed or denied with its rule, and one statement per `tools/list`.

mcpproxy refusals, such as a budget or a rug pull, reach the session as activities.

A rule reload ends the open MCP sessions. The next message on one is refused, and the client initializes again under the new rules.

A change to the lane itself (`upstream`, `listen`, the `mcp_gateway` block) needs a restart, as for every listener.

### What the audit records

Each statement carries this metadata:

| Key | On | Value |
|---|---|---|
| `mcp.method` | every statement | `tools/call` or `tools/list` |
| `mcp.tool` | a call | the real name of the tool called |
| `mcp.session` | every statement | the `Mcp-Session-Id` of the MCP session |
| `mcp.tools_hidden` | a catalog statement | the tools an `mcp_tool` rule left out, comma-separated |
| `mcp.sql_statements` | a call to a SQL tool | the number of SQL statements in its argument |
| `mcp.sql_argument`, `mcp.sql_dialect` | a SQL statement | the `argument` and `dialect` of its `mcp_gateway.sql` entry |
| `mcp.sql_index` | a SQL statement | its position in the argument, from 1 |
| `sql.incomplete` | a SQL statement that is `unknown` | the reason, when the lexer has one |

The session also records these activities:

| Activity | When | Attributes |
|---|---|---|
| `mcp_initialize` | the client's `initialize` | `client`, `client_version`, `protocol_version` |
| `mcp_invalid_params` | a `tools/call` refused as invalid params | `reason` |
| `mcp_sql_unreadable` | a call to a SQL tool whose argument the lane cannot read | `tool`, `argument`, `reason` |
| `mcp_catalog_unreadable` | a `tools/list` result the lane cannot read; the session ends | `reason` |
| `rules_reloaded` | a rule reload ends the session | `reason` |
| `mcp.tool_denied` | mcpproxy refuses a call, such as an unadvertised tool or a budget | `tool`, `rule`, `reason` |
| `mcp.budget_exceeded` | a budget or a rate limit refuses a call, or a result is cut | `tool`, `rule`, `reason` |
| `mcp.tools_changed` | a rug pull, or the server announces `tools/list_changed` | `tool`, `rule`, `reason` |
| `mcp_session_killed` | the lane ends the session: a rug pull with `on_rug_pull: kill`, or a catalog it cannot read | `reason` |
| `mcp.session_refused` | a request from another caller names the session; it gets a 404 | `caller`, `reason` |

A call a guardrail rule or OPA denies is a statement with its rule, not an activity.

## Metrics

Sidecar 1.302.0 and later.

`GET /stats` lists the lane. `active` and `total` count MCP sessions.

`denied` counts the messages the lane refused, in both directions: by a rule or OPA, as invalid params, and by `mcp_gateway` (a budget, a rate limit, a tool the server did not list, a rug pull). A request that the caller token check refuses does not count.

```json
{"name": "github-mcp", "addr": "127.0.0.1:18901", "active": 1, "total": 3, "denied": 2}
```

With a [`telemetry`](/setup/configuration/hoop-sidecar/telemetry) block, the lane exports `hoop.sidecar.mcp.messages`, a counter of every message:

| Attribute | Value |
|---|---|
| `hoop.lane`, `hoop.protocol` | as on every series |
| `hoop.direction` | `client` or `server` |
| `hoop.mcp.method` | the JSON-RPC method, such as `tools/call`. A response has none. A method MCP does not define is `(other)`. |
| `hoop.mcp.tool` | the real name of the tool a `tools/call` names, or of the call a response answers. `(other)` for a tool that is not among the first 1024 tools the server listed, and for a call refused as invalid params. |
| `hoop.mcp.decision` | `allow`, `deny`, or `kill`: the message ended the session |

The method and tool labels are bounded, so a client cannot add series.

Each tool call also counts in `hoop.sidecar.statements`. With traces on, each tool call is a trace of its own: a `hoop.statement` span with its stages.

```promql
# tool calls per second, by tool and decision
sum by (hoop_mcp_tool, hoop_mcp_decision) (rate(hoop_sidecar_mcp_messages_total{hoop_mcp_method="tools/call"}[5m]))
```

## Auth

The lane can check a caller token. It sends no credential to the upstream except a mutual TLS certificate.

### Caller to lane

| Option | Config | The audit names |
|---|---|---|
| none, the default | | `anonymous` |
| `identity_header` | `identity_header: x-forwarded-email` | the header's value |
| `caller_token` | see [Caller token](#caller-token) | the token's `name` |

`identity_header` names a caller and verifies nothing: any process that reaches the port can set it. Use it only behind a proxy on the same host or pod that authenticates the caller and sets the header.

Callers the lane cannot tell apart share the `anonymous` identity, so any of them that holds a session id can use that session.

Not supported yet: a verified identity per user, and OAuth login of MCP clients.

### Caller token

`caller_token` admits a caller by a shared token, so the lane can listen on an address other than loopback. Sidecar 1.290.0 and later; older builds refuse the key at `-validate`.

```yaml config.yaml
listeners:
  - name: github-mcp
    protocol: mcp
    listen: 0.0.0.0:8443
    upstream: https://mcp.example.com/mcp
    downstream_tls: {cert_file: /etc/tls/tls.crt, key_file: /etc/tls/tls.key}
    caller_token:
      header: X-Hoop-Token                       # the default
      file: /etc/hoop-inspect/caller-tokens      # one token per line; required
      name: claude-code                          # the principal in the audit trail; required
```

The MCP client sends the token on every request:

```bash
claude mcp add --transport http github https://relay.example.com:8443/mcp \
  --header "X-Hoop-Token: $HOOP_CALLER_TOKEN"
```

- **What is refused.** No header, an empty value, a value not in the file, or the header sent twice. The request gets a 403 `request refused: <reason>` before the lane reads its body, and the connection closes. Claude Code shows the server as `needs-auth`.
- **403, not 401.** A 401 sends MCP clients into OAuth discovery, which the lane does not serve.
- **Refusals are logged, not audited.** No MCP session exists yet. The Sidecar logs `mcp request refused` with the peer address and the reason.
- **What is admitted.** The session and every statement name `name` as the principal.
- **A session belongs to its token.** An `Mcp-Session-Id` works only with the token that opened it. A request with another token gets a 404, and the session records `mcp.session_refused`.
- **The token stays in the Sidecar.** The lane removes the header first. The token never reaches the upstream, an audit row, policy input or a log.
- **Refused at startup.** A `header` that MCP uses (`Mcp-*`, `Last-Event-ID`), or one the upstream, HTTP framing or the Sidecar already uses, such as `authorization` or `host`. `caller_token` together with `identity_header`.
- **No TLS of its own.** The token travels as written. Set `downstream_tls`, or put TLS in front of the listener.

The file, rotation and revocation work as on the `http` lane. See [Caller token](/setup/configuration/hoop-sidecar/protocols/http#caller-token).

### Lane to upstream

| Option | Config |
|---|---|
| no credential: a server on a private network, or one that holds its own credential | `upstream: https://mcp.internal.example.com/mcp` |
| mutual TLS | `upstream_tls: {cert_file: /etc/tls/client.crt, key_file: /etc/tls/client.key, ca_file: /etc/tls/ca.pem}` |

The lane sends no `Authorization` header to the upstream, the caller's included. It refuses `headers`, because the config holds no inline secret.

For a server that needs a bearer token or OAuth: run the MCP server yourself with its credential, or run a proxy on loopback that adds the credential, and point `upstream` at that proxy (`http://127.0.0.1:<port>/mcp` is accepted on loopback).

Not supported yet: a token from a file or a secret source and the caller's own token, OAuth to the upstream, and AWS SigV4.

---

## Limits

- `listen` takes an address other than loopback only with `caller_token`. See [Caller token](#caller-token).
- No call can be held for approval. See [AI analyzer](#ai-analyzer).
- `max_conns` and `network: unix` are refused.
- Sessions live in memory: run one replica, or pin `Mcp-Session-Id` to one.
