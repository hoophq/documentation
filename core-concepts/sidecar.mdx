The Sidecar is where runtime control happens. It is a proxy that runs next to the resource it protects, decodes the wire protocol between a client and that resource, and decides what reaches the resource and what comes back.

It is a single binary with no external dependency — one config file is the whole setup. Pick the path that fits how you run things: a quick binary install for a laptop or a VM, an official container image, or a Helm chart if you're on Kubernetes.

## How a request flows

A listener decides how requests behave inside the Sidecar. Every request takes one of two paths, and both end at the resource or at a denial.

**Direct access** sends the request straight through. Guardrails and Data Masking apply inline, deterministically, with no model call. See [Direct Access](/features/direct-access).

**Agentic access** routes the request through the AI Analyzer first. The analyzer classifies the statement and the risk level picks a tool: block it, allow it, hand it to a Guardrail, mask what comes back, or hold it for approval. See [Agentic Access](/features/agentic-access).

The two features — [Guardrails](/features/guardrails) and [Data Masking](/features/data-masking) — are reachable from both paths. A listener can use one, the other, both, or neither.

## What it can read

The Sidecar picks a codec per listener, and the codec decides how much of the traffic is legible.

| Protocol | On the request | On the response |
|---|---|---|
| `postgres` | full statement text, its worst effect, every effect, and each relation as a read or a write | result columns, row count, masking by re-framing |
| `clickhouse` | native Query text, query id, operation and tables | typed result columns, row count, bounded LZ4 decoding and masking by block re-framing |
| `mssql` | SQLBatch, every RPC call (`sp_executesql` unwrapped, prepared handles resolved, other procedures as `EXEC <name>`), a readable login | result columns and OUTPUT parameters, masking by re-framing the TDS token stream |
| `mongodb` | every `OP_MSG` command as Extended JSON, its operation and collections | result documents, masking by BSON field name and re-framing |
| `http` | method, path, normalized resource; body and headers only when the listener opts in with `http.capture_body`; the request body also when the listener holds for approval, or on the routes of an `http.sql` block | status; body and headers under the same setting |

The HTTP codec captures **nothing** by default: no bodies, no headers. A listener that holds for approval, or reads SQL with `http.sql`, captures request bodies. Everything captured reaches the guardrails engine, the audit trail and, where an analyzer is configured, a third party, so each listener opts in explicitly.

## How many listeners

**One listener per upstream. One process runs as many listeners as you declare.**

A listener is one bind address in front of one upstream, speaking one protocol, with its own set of rules. `listeners` is a list in the config file, so protecting a second resource means adding a second entry — not starting a second Sidecar:

```yaml
listeners:
  - name: appdb                   # listener 1: Postgres
    protocol: postgres
    listen: 127.0.0.1:15432
    upstream: db.internal:5432

  - name: billing-api             # listener 2: HTTP, same process
    protocol: http
    listen: 127.0.0.1:18080
    upstream: billing.internal:8080
```

Startup reports the count it resolved, so you always know how many you got:

```
config OK: 2 listener(s)
```

Three rules follow from this:

- **Listeners are independent:** each one picks its own protocol, bind address and transport. Moving one to a unix socket leaves the other on its TCP port.
- **Rules are per listener:** top-level `guardrails`, `opa` and `mask` are defaults every listener inherits, and any listener can override them. A strict production database and a permissive staging one live in the same process.
- **Audit is per listener:** every event carries the listener's `name`, so one Sidecar serving three resources still produces three separable trails.

Most deployments run a single listener. Add a second when the same workload reaches more than one protected resource.

See [Listeners](/setup/configuration/hoop-sidecar/config-file#listeners) for every field.

## Where the process sits

The Sidecar is a single binary with no external dependency, so placement is only a question of who can reach it:

- **Beside one workload:** a container in the same pod, reached over a unix socket. No port is opened, so reachability becomes a filesystem question rather than a network one.
- **On a host:** a plain process binding a TCP port. Nothing to mount, nothing to chown.
- **Behind an existing proxy:** Envoy, or anything that can forward plaintext to a local port. The Sidecar is an ordinary upstream, with no ext_proc, no WASM and no custom filter to install.

Nothing above the transport changes between these. Guardrails, masking and audit behave identically, because the Sidecar reads a connection and never asks what kind it is.

## Denials the user can read

When a rule denies a statement, the Sidecar writes the refusal in the protocol's own frame, always to the client, carrying the message the operator wrote in the config file:

| Protocol | Frame |
|---|---|
| `postgres` | pgwire `ErrorResponse`, `FATAL` `42501` |
| `clickhouse` | native `Exception`, code `497` |
| `mongodb` | `OP_MSG` command error, code `13` `Unauthorized` |
| `http` | `403` with an `X-Hoop-Denied` header |

A developer reads the reason in `psql` instead of watching a connection drop.

## Audit

Every session is recorded whether or not it issues a statement, so a client that connects and disappears still leaves a trace. Events are JSON lines written to stdout or a file, and the write happens **before** the forward: a crash between the two cannot lose the record of the statement that caused it.

### The six event kinds

| Event | Fires when | Carries |
|---|---|---|
| `session_start` | a connection is accepted, or an `http` lane's caller changes | principal, protocol, listener name |
| `statement` | a statement is inspected and allowed | text, operation, tables, `allowed=true` |
| `violation` | a statement is denied | the same, plus the rule that denied it and the message the client read |
| `masked` | a response was rewritten | entity names and a cell count, never the values |
| `error` | a transport or upstream failure | the error text |
| `session_end` | the connection closes, or an `http` lane's caller changes | duration, statement and denial totals |

A denial writes `violation` **instead of** `statement`, not in addition to it, so pulling every denial never means scanning every statement anyone ever ran.

### The admin API

The Sidecar serves a small HTTP interface on two listeners of its own, separate from every data lane. `admin.listen` (`127.0.0.1:19000` by convention) serves the probes and the token-gated ICA drain. It serves no audit data and no lane rules, so a platform can probe it. `/readyz` on it reports the process status as JSON. `admin.api_listen` (`127.0.0.1:19002` by convention) serves the read routes: what config the process resolved and what it recorded. It is off unless you set it.

```yaml
admin:
  listen: 127.0.0.1:19000       # /healthz /readyz, POST /v1/drain (ICA, token-gated)
  api_listen: 127.0.0.1:19002   # /stats /metrics /config /events /api/*
```

`api_listen` must not bind the same address and port as `listen`. If either listener cannot bind, the Sidecar stops.

| Listener | Endpoint | Returns |
|---|---|---|
| `admin.listen` | `GET /healthz` | `ok`, while the process runs. That includes the time the Sidecar waits for its Control Plane at boot. What a container healthcheck polls. |
| `admin.listen` | `GET /readyz` | `200` when a configuration is loaded and every listener serves, else `503`, with the status as JSON (below). With `admin.ica_readiness_json`, the ICA attestation instead: `status`, `inspection_enabled`, `graphics_bypassed`, `protocol_validation_enabled`. |
| `admin.listen` | `POST /v1/drain` | Drains the ICA lanes. Needs their deployment token. |
| `admin.api_listen` | `GET /stats` | Live counters, plus one line per listener with the address it really bound — a path means unix, a `host:port` means TCP. With a `telemetry` block, how many audit events the exporter sent and dropped. |
| `admin.api_listen` | `GET /metrics` | Prometheus [metrics](/setup/configuration/hoop-sidecar/risk-analysis#metrics). To push them over OTLP instead, see [OpenTelemetry](/setup/configuration/hoop-sidecar/telemetry). |
| `admin.api_listen` | `GET /config` | The **resolved** config: each listener's guardrails after inheritance, its OPA endpoint, and the analyzer settings with the credential omitted. |
| `admin.api_listen` | `GET /events` | The last N events from an in-memory ring buffer. |
| `admin.api_listen` | `GET /api/sessions` | One row per session: principal, connection, statement / denial / mask counts, and a verdict. |
| `admin.api_listen` | `GET /api/events` | Individual events, filterable. |
| `admin.api_listen` | `GET /api/stats` | Aggregates: totals, plus breakdowns by connection and by rule. |

On `admin.listen`, the read routes answer `404` with `moved: this route is served on admin.api_listen, which is off unless set`.

Releases up to 1.306 served the read routes on `admin.listen`. After the upgrade, a scraper or script that reads them needs `api_listen` set and its URL moved to that port. The Control Plane does not send `api_listen` to an older Sidecar, because that Sidecar refuses a config with a key it does not know.

To probe a port other than `admin.listen`, set the environment variable `HOOP_SIDECAR_HEALTH_LISTEN` to a `host:port`. It binds one more listener with `/healthz` and `/readyz` only. It binds when the process starts, before the configuration is known, so it answers while the Sidecar waits for its Control Plane: `/healthz` `200`, `/readyz` `503` with `waiting_for_control_plane`. `admin.listen` comes from the configuration, so it binds only after the first handshake.

### The `/readyz` body

Probes read the status code. The body is for the person who reads it:

```json
{
  "status": "ready",
  "process_running": true,
  "pid": 7,
  "valid_license": true,
  "config_loaded": true,
  "lanes_open": true,
  "control_plane_enabled": true,
  "connected_to_control_plane": false,
  "control_plane": {"last_handshake": "2026-11-23T17:40:12Z", "error": "unreachable"},
  "lanes": [{"name": "paymentsdb", "protocol": "postgres", "state": "open"}]
}
```

| Field | Meaning |
|---|---|
| `status` | `ready` (`200`) or `not_ready` (`503`) |
| `reason` | On `503` only: `waiting_for_control_plane` (no configuration yet, the Control Plane has not answered), `starting` (the configuration is not loaded yet), `lanes_not_open` (a listener does not serve) or `stopping` (the Sidecar is shutting down; `/healthz` stays `200` until it exits) |
| `valid_license` | A license in force that has not expired. It does not change the status code. |
| `config_loaded`, `lanes_open` | A configuration is loaded; every listener serves |
| `control_plane_enabled`, `connected_to_control_plane` | The Sidecar uses a Control Plane; its last handshake got an answer |
| `control_plane` | `last_handshake` (UTC), `error` of the last failed handshake (`unreachable`, `timeout`, `server_error`, `no_config`, `refused`), `boot_attempts` |
| `lanes` | One entry per listener: `name`, `protocol`, `state` (`open`; `starting` before it binds; `not_ready` while an ICA engine loads or drains, a gRPC listener waits for its schema, or an MCP listener is not bound; `closed` once it stopped accepting) |

A Control Plane lost after the configuration loaded never makes `/readyz` `503`: the listeners keep serving the last good configuration, and only the body says so. The body holds codes and listener names, never an error message, a URL, a token or a license. Earlier releases answered `/readyz` with plain text (`ready`, `not ready: <lane names>`).

`GET /config` is the one to reach for when a rule you wrote never fires. Inheritance is merged at startup, so the file tells you what you asked for and `/config` tells you what the process resolved:

```bash
curl -s localhost:19002/config | jq '.lanes[] | {name, rules}'
```

The query endpoints filter on `principal`, `connection`, `protocol`, `since`, `until`, `denied`, `open`, and `q` for substring search, with `limit` and `cursor` for paging. `/api/events` also takes `session_id` and a repeatable `kind`.

Both in-memory views are off by default, and each has its own budget: `audit.memory_buffer` sets how many events `/events` keeps, `audit.query_sessions` how many sessions back `/api/*`. Zero on either disables that surface without touching the JSON lines stream, which stays the record of truth.

<Warning>
The read routes on `admin.api_listen` have no authentication and no CORS of their own, and they serve every statement every user ran. They are off by default. When you turn them on, keep `api_listen` on loopback, or put it behind whatever already gates access to your audit trail. Never expose it on a data port.
</Warning>

Where those events go on the way out — the bounded async queue, the file, and the two in-memory sinks — is in [Architecture](/setup/configuration/hoop-sidecar/components#audit-six-kinds-one-write-path-three-sinks). To watch the Sidecar from Grafana, Honeycomb or Datadog — statements per lane, denials, and where each statement's time goes — see [OpenTelemetry](/setup/configuration/hoop-sidecar/telemetry).
