A Sidecar listener that [swaps credentials](/features/credential-swap) needs to know two things the config file cannot tell it: which people may log in, and whose session a workload's connection is. Both live on the Control Plane and reach the Sidecar with its configuration, on the heartbeat, so a change is in force within a minute and no process restarts.

---

## Who may reach a lane

Access to a lane is a **grant**: a user or a group, named by an admin, for one Sidecar and one listener. Without a grant nobody can mint a key for that lane, so the grant list is the entitlement.

```bash
# the dba group may use the appdb lane of the sidecar named shared-eu
curl -X POST "$HOOP_URL/api/sidecars/shared-eu/lanes/appdb/grants" \
  -H "Authorization: Bearer $HOOP_TOKEN" \
  -d '{"group_name": "dba"}'

# one person
curl -X POST "$HOOP_URL/api/sidecars/shared-eu/lanes/appdb/grants" \
  -H "Authorization: Bearer $HOOP_TOKEN" \
  -d '{"subject": "jane@acme.com"}'
```

| Route | Role | Does |
|---|---|---|
| `GET /api/sidecars/{name}/lanes/{lane}/grants` | admin | lists the grants of a lane |
| `POST /api/sidecars/{name}/lanes/{lane}/grants` | admin | adds one; the body is `{"subject": ...}` or `{"group_name": ...}`, not both |
| `DELETE /api/sidecars/{name}/lanes/{lane}/grants/{id}` | admin | removes one; keys already minted keep working until they expire or are revoked |

`subject` is the user's email or id. Groups come from the Control Plane's user groups, which an identity provider mapping fills.

## The key a person logs in with

A user who holds a grant mints a key after signing in. The key is shown once; the Control Plane stores a hash.

```bash
hoop sidecar credential shared-eu/appdb --expires 24h
```

```
user:  jane@acme.com
key:   hlc_3fQ9...
postgres:  PGPASSWORD='hlc_3fQ9...' psql "host=<sidecar> port=<port> user=jane@acme.com sslmode=require"
```

The same through the API: `POST /api/sidecars/{name}/lanes/{lane}/credentials` with `{"expires_in_hours": 24}`. The default is 24 hours and the most is 720. The response carries `user`, `key`, `expires_at` and the lane's protocol; the key goes where the client keeps a password: `PGPASSWORD`, `.pgpass`, the MongoDB URI, an `Authorization: Bearer` header on an HTTP lane.

| Route | Role | Does |
|---|---|---|
| `POST /api/sidecars/{name}/lanes/{lane}/credentials` | user | mints a key; `403` without a grant, `404` when the lane is not in the Sidecar's configuration, `422` when the Sidecar's last handshake did not declare it can read a credential set |
| `GET /api/users/me/sidecar-credentials` | user | the caller's keys, without the key material |
| `DELETE /api/sidecar-credentials/{id}` | user, admin | revokes one; a user revokes their own, an admin anyone's |

A key is bound to one Sidecar and one lane. Presented anywhere else it matches nothing. Expiry is enforced by the Sidecar's own clock, so a Sidecar that lost the Control Plane still refuses an expired key.

### How the Sidecar learns about it

With every heartbeat the Control Plane serves the Sidecar a `credential_set`: for each valid key of that Sidecar, the hash, the person, their groups, the lane and the expiry, plus the SCRAM material the Postgres and MongoDB drivers need. Only that Sidecar's keys, never the whole organization's. A mint is accepted at the next login after the next heartbeat; a revocation is refused the same way. The Sidecar never calls the Control Plane on the connect path.

## The person a Sidecar acts for

A listener with `identity: {type: none}` trusts the unix socket: whoever reaches it is the caller. That is the right model for one workload per pod, but the Sidecar still needs to know whose workload it is. `owner_email` on the Sidecar says so.

```bash
curl -X PUT "$HOOP_URL/api/sidecars/ws-jane" \
  -H "Authorization: Bearer $HOOP_TOKEN" \
  -d '{"owner_email": "jane@acme.com", "configuration": {...}}'
```

`owner_email` is on `POST /api/sidecars`, `PUT /api/sidecars/{name}` and the Sidecar's page in the web app. A GitOps reconciler that creates one Sidecar per user pod writes it with the rest of the entry, from the same source that creates the pod. The pod proves which pod it is with its service account token (see [Sidecar service accounts](/setup/configuration/hoop-sidecar/service-accounts)); the Control Plane row says whose it is. Neither fact enters the pod.

A Sidecar without an owner behaves as before: sessions carry the pod's name, holds are filed under the Sidecar, nothing is refused. Adding the owner later changes the next hold, not the running process.

## Who hears about a hold

A statement a Sidecar holds for approval is filed under a person:

1. the principal the Sidecar verified at login, when the lane has an `identity`;
2. else the Sidecar's `owner_email`;
3. else the Sidecar's name, as before.

Slack posts to the lane's approver channel as configured in [Slack](/control-plane/slack), and additionally sends a direct message to the person when their hoop account is linked to Slack: once when the statement is held, once when it is approved or denied. The approver sees who asked; the requester does not have to watch a channel.

This behaviour is gated by the feature flag `experimental.sidecar_review_owner`, on by default. Switching it off at Settings → Experimental restores the previous filing under the Sidecar's name, with no direct message.

## Rolling out across a fleet

Everything here is additive, so a fleet moves at the pace a reconciler applies entries:

- A Sidecar with no owner and lanes with no `identity` keeps its current behaviour.
- A grant and a key change nothing until a lane carries `identity: {type: hoop_credential}`; a lane can take the allowlist of `passthrough_users` first, then the verifier, then drop the allowlist.
- A Sidecar build that cannot read the new keys is never served them. The Sidecar page shows what the build declares; a mint for a lane on such a Sidecar is refused with `422` and the reason.

### Moving a pod's identity to SPIRE

A Sidecar row is bound to the first identity that reaches it and refuses a second one. A pod that switches from a Kubernetes service account token to a SPIFFE JWT-SVID is a second identity. Per pod, in one pass: switch the chart to `controlPlane.identity: spiffe`, clear the binding with `DELETE /api/sidecars/{name}/identity`, let the next handshake rebind through a [sidecar service account](/setup/configuration/hoop-sidecar/service-accounts) that names SPIRE's issuer. Done out of order, the pod comes up and its row refuses it. Owner, grants, rules and Slack channels do not move.
